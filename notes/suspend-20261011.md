# Suspend (s2idle) and autosleep (2026-10-11)

## What the kernel offers

`/sys/power/state` = `freeze mem disk`; `mem_sleep` = `[s2idle]` only, as on Android. No `pm_test`, no
`/sys/power/autosleep`, no `pm_wakeup_irq`. The wake reason comes from the kernel log: `Resume caused by IRQ N, name`.
Reading `/sys/power/wakeup_count` blocks while a wakeup source is active: don't. With the cable in,
`11201000.usb0` holds a wakeup source, but a direct `echo mem > /sys/power/state` ignores wakeup sources (only the
wakeup_count protocol honours them).

## First attempts (staged test: `vegas-suspend-test`, RTC alarm +15 s)

1. Screen on: **pd-chk-mt6835 refuses**, "mm_infra is on" (GCE, SMI MDP sub-common held by the display path). The
   suspend aborts cleanly and everything resumes. Android always turns the display off first.
2. Screen off (`hl.dsp.dpms disable`) first: **clk-chk-mt6835 refuses** at suspend_noirq once (some clock on; the
   kernel log ring had rotated before it could be read, so the journal is used now).
3. **alarmtimer -EBUSY** once: a kernel alarm due within 2 s (likely the charger/gauge). A timing race.
4. With retries (up to 5): **success on the first try.** `PM: suspend entry (s2idle)` … `Resume caused by IRQ 365,
   rcs_irq` (the PMIC's SPMI interrupt: `charger_pm_event: alarm timeout, wake up charger`). Kernel time doesn't
   advance in s2idle; the wall clock showed 5 s. Wi-Fi stays associated and passes traffic after resume. The display
   comes back, the GPU and touch resume.

Noise on resume, harmless: the microSD controller (11240000.mmc) retunes with cmd19 CRC errors (the card is only the
rescue copy), `consys_check_reg_readable` from the Wi-Fi combo chip, and a WARN stack in `mtk_drm_sys_suspend`/`resume`.

## Autosleep

- `vegas-power-key` (session) creates `$XDG_RUNTIME_DIR/vegas-screen-off` when it turns the screen off and removes
  it when it turns it on.
- `vegas-autosleep.service` (root, `/usr/local/libexec/vegas/autosleep`, also started by native-init): after 5 s of
  screen-off it writes `mem` to `/sys/power/state`, retrying up to 5 times when a checker refuses. After each wake
  it stays up 2 s (enough for a power key press to reach vegas-power-key), then sleeps again while the marker exists.
- Stays awake while `/var/lib/vegas/no-suspend` exists, **while USB data is connected** (gadget `configured`, so
  the laptop's recovery endpoint keeps working; a plain charger still allows sleep), while a playback PCM is
  RUNNING, or if vegas-power-key isn't running. `VEGAS_SLEEP_IGNORE_USB=1` is for testing over the cable.
- Wake source: the power key has `wakeup-source` in the DT (`mt6377keys/power`), and mtk-pmic-keys calls
  `enable_irq_wake` for it on suspend. Its IRQs go through the same PMIC SPMI interrupt (rcs_irq) that already woke
  the phone.
- Test over USB with the inhibitor off: screen off, then `slept 11s, woke: IRQ 365, rcs_irq`, then three times
  `slept 8s` (charger wakes while plugged in). A power key event in an awake window turned the screen on and ended
  the loop. Log: /var/log/vegas/autosleep.log.

## Notifications while asleep: wake on Wi-Fi + sync windows

- Default WoWLAN is off (`iw phy phy0 wowlan show`: disabled). With the laptop's ARP entry cached, unicast pings
  to the sleeping phone **don't wake it and get no answer**; it only woke for the charger. The laptop's ARP then fails.
- nl80211 offers only `any`, `disconnect` and `magic-packet` on this driver (no patterns). The gen4m driver also
  has wifi.cfg keys (`WowEnable`, `WowDetectType`, `WowOnMdtim`, …); not explored (no source here). In MediaTek's
  related mt7668 driver, WoW is enabled with the private command `set_wow_enable`.
- **`iw phy phy0 wowlan enable any`: 25/25 pings answered**, each waking the phone (`IRQ 138, wlan0`) within
  10–290 ms. Push messages arrive at once, as on Android.
- The cost: the firmware can't drop broadcasts (Android's APF does). In 30 s on this LAN, wlan0 received:
  - 13 unicast TCP packets for the phone's own Chrome (a web app's live connection to a Cloudflare-hosted site)
  - 6 Syncthing LAN-discovery broadcasts (UDP 21027, every ~5 s from the laptop's Syncthing)
  - 8 mDNS packets and 4 IPv6 multicast ICMPv6 packets

  Idle over 2 min: wakes about every 5 s, asleep 50% with a fixed 2 s grace.
- **Traffic-based grace:** after a Wi-Fi wake, stay up 1 s, extended while wlan0 receives > 1500 B/s (up to 15 s;
  a push message is a few KB, a broadcast < 500 B). Asleep 63% on the same LAN, phone screen off.
  Rough budget: ~25–30 mA average vs ~8 mA purely asleep, i.e. about a week of standby instead of weeks. Worth it
  for instant notifications on a phone charged daily. Opt out with `/var/lib/vegas/no-wake-on-wifi`.
- **Sync windows** (both modes): the RTC wakes the phone every 15 min for 30 s (`VEGAS_SLEEP_SYNC_MIN`/`_S`), like
  Doze's maintenance windows; tested with 1 min/10 s. Wi-Fi power save is on while the screen is off and back off
  when it's on.
- Possible improvement: stop the phone's Chrome web apps' live connections while the screen is off (freeze the
  renderers, as Android Chrome does with background tabs); and Syncthing on the LAN is the main broadcast source here.
- A lock screen.

## Screen timeout

vegas-power-key also watches the touchscreen and mtk-kpd (read-only, no grab) and turns the screen off after
`~/.config/vegas/screen-timeout` seconds without input (default 60, 0 = never). It stays on while a playback PCM is
RUNNING (video) and while USB data is connected (Android's "stay awake while charging" developer option, which keeps
the laptop's screenshots working; `VEGAS_TIMEOUT_IGNORE_USB=1` for testing). Tested with a 12 s timeout: a touch at
8 s kept the screen on at 17 s, it was off by 27 s, and the power key turned it back on.

## Critical battery

Omarchy's shell warns at 10% (UPower, "Time to recharge!"). `vegas-battery-guard.timer` (every minute, root,
`libexec/vegas/battery-guard`) adds Android's last step:
- at ≤ 3% while discharging: a critical notification ("Plug in the charger within a minute") plus a long vibration
- if the phone is still unplugged ~60 s later: a clean `power-transition poweroff`, instead of a hard PMIC
  undervoltage cut on the ext4-in-userdata root
- plugging in, or a higher reading, cancels it

Notifications from root go through `libexec/vegas/session-run`: it runs a command as the user in the desktop's own
D-Bus/Wayland environment, copied from the running quickshell. Tested with `VEGAS_TEST_CAPACITY=2
VEGAS_TEST_STATUS=Discharging VEGAS_DRY_RUN=1`. Opt out with `/var/lib/vegas/no-battery-guard`.
**`power-transition poweroff` verified on battery (2026-10-11 13:42):** Shutdown from the power menu with the cable
out powered the phone off (all supplies offline in `last-request.log`), and the power key booted it again.

## Charge limit (battery protect)

`vegas-charge-limit 50..95|off|status` plus `vegas-charge-limit.service`. **Off by default**, as Motorola's Battery
Protect is opt-in. It uses Motorola's adaptive-charging switch in the MediaTek charger driver:
- `mtk-master-charger/current_max` ← non-zero sets `adaptive_charging_disable_ibat`: charging stops and the power
  path stays on, so USB powers the phone and the battery neither charges nor cycles. 0 clears it.
- Tested: the battery current went 600 mA → 0 with USB online, and back. With a 90% limit at 95%: "charging paused",
  and the driver logs `disable_ibat = 1`.
- It resumes 5 points below the limit, and stopping the service always re-enables charging.

Rejected alternatives:
- Motorola's retail demo mode (`force_demo_mode`, 35–80): it can't be turned off without a reboot, and it cuts
  input power, so the battery cycles.
- MediaTek smart charging (`enable_sc`/`sc_tuisoc`): it charges to 100% before its daily window ends.
